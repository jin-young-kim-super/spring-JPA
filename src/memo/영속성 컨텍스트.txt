JPA에서 가장 중요한 2가지
1. JPA을 고려해서, 어떻게 객체 모델링-RDB 설계할 것이냐?(추후에 학습 예정)
2. 영속성 컨텍스트 - JPA의 내부 동작 원리(이번 시간부터 학습할 내용)


강의 자료 그림에도 나와 있지만, 당연한 이야기이지만, 엔티티 매니져는 커넥션의 풀의 커넥션을 반드시 획득해야만 한다. 
그리고 요청마다 엔티티 매니저는 생성이 되고, 절대 엔티티 매니저를 다른 쓰레드와 공유하지 않는다. 



영속성 컨텍스트(Persistence Context)
-> "엔티티를 영구 저장하는 환경"(지금 이해 ㄴㄴ)
여기서는 일단 엔티티 매니저를 획득하면 그 내부에 자동으로 영속성 컨테이너도 생성된다는 것을 알아두자.


엔티티의 생명 주기
STEP 1. 비영속 상태 : 객체가 컨텍스트에 영속되지 않은 상태(=그냥 객체를 생성하기만한 상태)
// 객체를 생성한 상태(비영속)
Member member = new Member()
member.setId("helloA");
member.setUsername("member"A);
-> 아래에서 영속 상태를 배우겠지만, 엔티티 매니저를 거치지 않은 엔티티 객체는 JPA의 관리 대상이 아님으로 영속성 컨텍스트에 들어 가지 않는다.

STEP 2 -1. 영속 상태 : 엔티티 매니저를 통해서 객체가 저장(persist)된 상태
-> 반드시 엔티티 매니저를 통해서 무언가를 실행해야 영속성 컨텍스트의 관리 대상이 되어서, 컨텍스트 안에 엔티티가 들어 가게 된다.

Member member = new Member()
member.setId("helloA");
member.setUsername("member"A);

EntityManage em = entityManager.createEntityManager()
em.getTransaction.begin();

// 객체를 저장(persiste)한 상태(영속 상태)
em.persiste(member); // 이 객체는 영속 컨텍스트에 들어 가며, 이제 JPA관리 대상이 된다.
                     // 정말 중요한 것은 이떄 DB에 저장되는 것이 아니고, 영속 컨텍스트에 저장됨에 주의하자
                     // JPA는 반드시 트랜잭션 커밋 시에만 영속성 컨텍스트에 저장된 객체를 바탕으로 SQL문이 작성돼 실행이 된다.

STEP 2-2. 준영속/삭제 상태
em.detach(member) // 영속성 컨테스트에서 엔티티 분리(준영속 상태)
-> 엔티티 객체가 영속성 컨텍스트에서 제거되어, 더이상 JPA의 관리 대상이 아니다.

em.remove(member) // 영속성 컨텍스트에서 엔티티 삭제(삭제 상태)
-> 엔티티 객체가 영속성 컨텍스트에서 절대 사라지는 것이 아니라 영속성 컨텍스트에 저장된 객체를, DB에서 해당 데이터 삭제를 해달라는 것이다.
그래서 삭제 상태는 트랜잭션 커밋 시 DELETE 쿼리문이 생성되지만 준영속 상태는 아무 쿼리문도 생성되지 않는다.


영속성 컨텍스트의 이점(캐싱과 Buffer Writing)
-> 영속성 컨텍스트처럼 중간에 뭔가가 있을 때는 캐싱과 Buffer Writing의 이점이 생긴다(다음 시간부터 자세히 학습)
1. 1차 캐시(캐싱)
2. 동일성 보장(캐싱)
3. 트랜잭션을 지원하는 쓰기 지연(transactional write-behind)(Buffer Writing)
4. 변경 감지(Dirty Checking)(Buffer Writing)
5. 지연 로딩(캐싱과 연관!! , 영속성 컨텍스트를 활용하지만 별도의 기능)

1. 1차 캐쉬(강의자료에 코드나 그림을 꼭 참조, 여기서는 강의 자료에는 없는 내용만을 기록)
ex)
Member member = new Member();
member.setId("member1");
member.setUsername("회원1");

//1차 캐시에 저장됨
em.persist(member);

//1차 캐시에서 조회(영속성 컨텍스트 안에서 1차 캐싱이 일어난다)
Member findMember = em.find(Member.class, "member1");

Q. 이렇게 영속성 컨텍스트에서 1차 캐싱의 이점은?
A. 코드를 보자
ex)
Member findMember2 = em.find(Member.class, "member2");
-> "member2"는 영속성 컨텍스트의 1차 캐시에 없기 때문에 내부적으로 DB에서 해당 객체를 조회해서 다시 영속성 컨텍스트에 있는 1차 캐시에 저장을 하고, 그 다음부터 애플리케이션 코드에서 member2를 find할떄는 SQL문 실행 없이 메모리에서 바로 조회 가능

중요 : 1차 캐싱은 그렇게 큰 도움이 안된다.
-> JPA의 1차 캐시는 트랜잭션이 종료되면 메모리에서 다 날라간다. (JPA의 모든 변경은 트랜잭션 단위였음을 기억하자)
고로, 트랜잭션이 살아 있는 동안의 그 짧은 시간에서만 캐싱이 허용되므로, 캐싱을 사용할 수 있는 시간이 매우 짧다. 그래서 JPA에서는 2차 캐시라고 해서 애플리케이션의 모든 요청 쓰레드에서 공유하는 캐시 기능을 제공하는데 2차 캐시에 비교를 하면 막 그렇게
성능 향상에 도움이 되지 않는다.(JPA의 2차 캐시는 나중에 다룰 지 모르겠다)


2. 동일성 보장/엔티티 신뢰성 보장(패러다임 불일치 해결, 단 같은 트랜잭션 내에서만 보장)
Member a = em.find(Member.class, "member1");
Member b = em.find(Member.class, "member1");
System.out.println(a == b); //동일성 비교 true


3. 트랜잭션을 지원하는 쓰기 지연

EntityManager em = emf.createEntityManager();
EntityTransaction transaction = em.getTransaction();

//엔티티 매니저는 데이터 변경시 트랜잭션을 시작해야 한다.
transaction.begin(); // [트랜잭션] 시작

em.persist(memberA);
em.persist(memberB);

//여기까지 INSERT SQL을 데이터베이스에 보내지 않는다.
//커밋하는 순간 데이터베이스에 INSERT SQL을 보낸다.
transaction.commit(); // [트랜잭션] 커밋
-> Buffer Writing을 통해서 SQL문을 1번만 실행되게 함으로 성능을 올린다
영속성 컨텍스트 안에는 1차 캐시말고도 쓰기 지연 SQL 저장소(Buffer)라는 것이 있다. persist()가 실행될 떄마다 1차 캐시에 저장됨과 동시에
쓰기 지연 SQL 저장소에 SQL문이 생성돼서 마치 버퍼에 차곡차곡 SQL문을 쌓아 둔다. 그러다가 커밋이 되면 SQL문을 한 번에 실행을 한다.
한 번만에 여러 SQL문을 보내므로 성능 향상에 도움이 된다.(JDBC에서는 이걸 Batch 쿼리라고 한다, 실제로 JPA는 결국 JDBC로 동작하기 때문에 내부적으로 이 JDBC의 BATCH를 사용한다)
<property name="hibernate.jdbc.batch_size" value=10/>라고 설정하면 batch에서 10개의 쿼리문을 한 번에 보낸다는 뜻이다.
물론 실무에서는 배치 쿼리문을 짜지 않는 이상 여러 개의 쿼리를 한 번에 날릴 일은 없어서 실시간 쿼리문 성능에 크게 도움은 안 되지만, 그래도 JPA의 Buffer Writing(혹은 batch_size 설정 한 줄)을 잘만 활용하면
성능을 올릴 수가 있다.

4. 변경 감지(Dirty Checking, 강의 자료 그림도 참조)
EntityManager em = emf.createEntityManager();
EntityTransaction transaction = em.getTransaction();
transaction.begin(); // [트랜잭션] 시작

// 영속 엔티티 조회
Member memberA = em.find(Member.class, "memberA"); // find()는 일반 조회라서 MVCC를 사용해서 Undo Log에서 가져옴

// 영속 엔티티 데이터 수정
memberA.setUsername("hi"); // 이 시점에는 객체의 값만 변경되지, UPDATE문이 작성되지는 않는다.
memberA.setAge(10); // 이 시점에는 객체의 값만 변경되지, UPDATE문이 작성되지는 않는다.

transaction.commit(); // [트랜잭션] 커밋 : flush/commit 시점에 영속성 컨텍스트 내에서 데이터의 최종적인 변경을 감지(Dirth Checking)을 하여 UPDATE문 작성이 된다
                      // 정확한 메커니즘은 강의자료 그림에도 나와있뜻이, memberA에 대한 객체값이 변경될 떄마다 영속성 컨텍스트 내의 memberA에 대한 스냅샵들이 저장되는데, 그 스냅샵들을 비교해서 최종적인 변경값을 추출한다.
                      // 그래서 커밋 이전에 em.update(memberA) 같은 코드가 필요가 없다
                      // -> 진짜 JPA의 철학처럼 애플리케이션 코드에서는 자바 컬렉션을 DB라고 생각하고 사용만 하면 된다. 참고로 flush는 commit 메서드 안에서 실행이 먼저 된다.

Q. setName, setAge은 UPDATE문일 텐데, 만약 다른 트랜잭션에서 해당 Member에 락을 걸어 놓은 상태라면 UPDATE는 락이 반환될 때까지 실행대기를 해야 하지 않나?
A. UPDATE SQL 실행에 있어서는 flush/commit 시 다른 트랜잭션에서 Lock을 걸었으면 Lock이 반환될 떄까지 기다린다.

Flush란?
영속성 컨텍스트 내의 변경 내용을 데이터 베이스에 반영하는 것! 더 정확히는 쓰기 지연 SQL 저장소에 있는 모든 INSERT/UPDATE/DELETE 쿼리문 등을 데이터 베이스에 날려 주는 것이다.

Flush 실행 흐름
1. 변경 감지(Dirty Checking)
2. 최종 수정된 쿼리문을 [쓰기 지연 SQL 저장소]에 등록
3. 쓰기 지연 SQL 저장소에 있는 모든 쿼리문을 데이터 베이스에 날림(flush의 본질)

영속성 컨텍스트를 flush하는 방법 3가지
1. entityManger.flush() - 직접 호출(많이 사용하지는 않지만, 테스트 코드에서 자주 사용)
2. 트랜잭션 커밋 - 자동 호출
3. JPQL 실행 - 자동 호출(이 부분은 추후에 자세히 학습 예정)

// memberA,B,C는 영속성 컨텍스트에만 현재 존재하고 데이터 베이스에는 아직 저장이 안 된 상태
em.persist(memberA);
em.persist(memberB);
em.persist(memberC);

//중간에 JPQL 실행(memberA,B,C를 데이터 베이스로부터 조회가 목적!!!)
query = em.createQuery("select m from Member m", Member.class);
List<Member> members= query.getResultList();
-> 위 JPQL 실행 시점에는 데이터 베이스에 아직 영속성 컨텍스트 내의 memberA,B,C가 저장이 안 돼 있기에 아무것도 조회가 되지 않는 대참사가 일어난다.
이러한 대참사를 방지하이 위하여 중간에 JPQL이 있을 떄에는 트랜잭션 내의 영속성 컨텍스트에 대해서 강제적으로 flush를 내부적으로 호출하여 데이터 베이스에 쿼리문을 실행시켜 버린다.



5. 지연 로딩
