JPA에서 가장 중요한 2가지
1. JPA을 고려해서, 어떻게 객체 모델링-RDB 설계할 것이냐?(추후에 학습 예정)
2. 영속성 컨텍스트 - JPA의 내부 동작 원리(이번 시간부터 학습할 내용)


강의 자료 그림에도 나와 있지만, 당연한 이야기이지만, 엔티티 매니져는 커넥션의 풀의 커넥션을 반드시 획득해야만 한다. 
그리고 요청마다 엔티티 매니저는 생성이 되고, 절대 엔티티 매니저를 다른 쓰레드와 공유하지 않는다. 



영속성 컨텍스트(Persistence Context)
-> "엔티티를 영구 저장하는 환경"(지금 이해 ㄴㄴ)
여기서는 일단 엔티티 매니저를 획득하면 그 내부에 자동으로 영속성 컨테이너도 생성된다는 것을 알아두자.


엔티티의 생명 주기
STEP 1. 비영속 상태 : 객체가 컨텍스트에 영속되지 않은 상태(=그냥 객체를 생성하기만한 상태)
// 객체를 생성한 상태(비영속)
Member member = new Member()
member.setId("helloA");
member.setUsername("member"A);
-> 아래에서 영속 상태를 배우겠지만, 엔티티 매니저를 거치지 않은 엔티티 객체는 JPA의 관리 대상이 아님으로 영속성 컨텍스트에 들어 가지 않는다.

STEP 2 -1. 영속 상태 : 엔티티 매니저를 통해서 객체가 저장(persist)된 상태
-> 반드시 엔티티 매니저를 통해서 무언가를 실행해야 영속성 컨텍스트의 관리 대상이 되어서, 컨텍스트 안에 엔티티가 들어 가게 된다.

Member member = new Member()
member.setId("helloA");
member.setUsername("member"A);

EntityManage em = entityManager.createEntityManager()
em.getTransaction.begin();

// 객체를 저장(persiste)한 상태(영속 상태)
em.persiste(member); // 이 객체는 영속 컨텍스트에 들어 가며, 이제 JPA관리 대상이 된다.
                     // 정말 중요한 것은 이떄 DB에 저장되는 것이 아니고, 영속 컨텍스트에 저장됨에 주의하자
                     // JPA는 반드시 트랜잭션 커밋 시에만 영속성 컨텍스트에 저장된 객체를 바탕으로 SQL문이 작성돼 실행이 된다.

STEP 2-2. 준영속/삭제 상태
em.detach(member) // 영속성 컨테스트에서 엔티티 분리(준영속 상태)
-> 엔티티 객체가 영속성 컨텍스트에서 제거되어, 더이상 JPA의 관리 대상이 아니다.

em.remove(member) // 영속성 컨텍스트에서 엔티티 삭제(삭제 상태)
-> 엔티티 객체가 영속성 컨텍스트에서 절대 사라지는 것이 아니라 영속성 컨텍스트에 저장된 객체를, DB에서 해당 데이터 삭제를 해달라는 것이다.
그래서 삭제 상태는 트랜잭션 커밋 시 DELETE 쿼리문이 생성되지만 준영속 상태는 아무 쿼리문도 생성되지 않는다.


영속성 컨텍스트의 이점(캐싱과 Buffer Writing)
-> 영속성 컨텍스트처럼 중간에 뭔가가 있을 때는 캐싱과 Buffer Writing의 이점이 생긴다(다음 시간부터 자세히 학습)
1. 1차 캐시(캐싱)
2. 동일성 보장(캐싱)
3. 트랜잭션을 지원하는 쓰기 지연(transactional write-behind)(Buffer Writing)
4. 변경 감지(Dirty Checking)(Buffer Writing)
5. 지연 로딩(캐싱)
