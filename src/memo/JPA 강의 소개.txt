JPA는 트랙터에 비유할 수가 있다. 
개발 트랜드의 변화
1. 순수 JDBC : 모든 SQL문 개발자가 작성/객체-테이블 매핑도 개발자가 일일이 다함
2. JDBC Templete, MyBatis : 객체-테이블 매핑 자동화/여전히 모든 SQL문을 개발자가 작성
3. JPA를 비롯한 ORM : 모든 SQL문 자동화/객체-테이블 매핑 자동화
-> 즉, JPA가 등장하고 나서, 개발 생산성/유지 보수성 존나게!! 그러나 사용하는 데에 있어서 많은 지식/학습이 필요(트랙터와 유사! 밭 가는 속도는 존나 빨라 졌지만, 그대신 트랙터의 사용법을 알아야 한다)

JPA가 실무에서 어려운 구체적인 이유
1. 튜토리얼만 보면 JPA로 굉장히 쉽고 빠르게 개발을 할 수 있을 것 같아서 실무에 바로 도입을 하면 100프로 망한다. 
-> 왜냐하면 결론부터 말을 하면 객체-테이블 매핑이 잘 되게 설계하는 법을 몰라서 그렇다. 실무에는 테이블과 객체의 종류가 수십 가지가 된다. 즉 정말 복잡하게 유기적으로 돌아가야 한다. 
그래서 튜토리얼처럼 테이블 1,2개를 전제로 하는 예제 코드만 보고 실무를 도입하는 하면 망한다.
그래서 강의에서는 객체-테이블을 제대로 매핑하도록 설계하는 법을 배운다.

SQL 중심 개발의 문제점
1. 현대는 애플리케이션 코드는 객체지향, 데이터베이스는 관계형 데이터베이스이다. 이 말은 지금 시대는 객체를 관계형 데이터 베이스에 저장하는 시대라는 뜻이다. 
-> 그래서 객체마다 이걸 SQL문으로 전환하는 코드를 모든 객체마다 다 일일이 만들어 줘야 한다는 것이다. 이 과정에서 반복되는 SQL문을 개발자가 일일이 객체에 맞게
직접 작정해야 한다는 점이다. 실무에서는 도메인 객체가 수십 개가 되는 데 각 도메인 객체에 맞게 일일이 SQL문을 다 작성해야 한다(INSERT, UPDATE, DELETE, 객체->SQL 전환 코드, SQL->객체 전환 코드 등)
이 과정은 생산성의 문제는 물론 유지보수 측면에서도 문제가 있다. 만약에 회원 도메인 객체에 필드명의 변경이 되면 모든 SQL문에 변경을 반영시켜 줘야 하고, 또 필드가 추가/삭제 되면 또 그때마다 모든 SQL문을 다 수정해야 한다. 

2. 패러다임 불일치 문제
1에서 언급했듯이 현대 애플리케이션 코드는 객체지향 개발이다. 그 말의 의미는 각 도메인 객체를 개발자가 관계형 데이터베이스에 맞게 SQL문을 일일이 매핑을 해줘야 하는 것이다. 
INSERT,UPDATE,DELETE문 등을 일일이 객체에 맞게 변환시켜줘야 한다는 것이다. 
그럼 왜 이런 변환이 반드시 필요한 걸까? 그건 객체지향과 데이터 베이스의 패러다임의 차이 떄문이다.

객체와 관계형 데이터 베이스의 패러다임 4가지 차이(상속/연관 관계만 설명 하겠다)
1. 상속
자바 객체에는 상속 개념이 있지만, 관계형 데이터 베이스에는 상속 개념이 없다. 그래서 생기는 매우 귀찮은 문제가 있다. 
예를 들어 Album이라는 객체가 있고, 그 객체는 Item이라는 객체를 상속받고 있다고 하자!!(강의 자료의 그림을 참조)
그럼 Album 객체를 RDB에 저장하기 위해서는 Album 객체를 Item과 Album 객체로 분해를 해서 CRUD SQL문을 만들어 줘야 한다. 
ex) 
INSERT ITEM....
INSERT Album....
-> 근데 만약에 Album의 상속 관계가 매우 복잡하면?? 상상만 해도 끔찍하다. 
더 끔찍한 것은 SELECT문이다. ITEM, ALBUM 테이블을 서로 막 조인하고 각각의 객체를 생성해서 매핑해주고 그걸 또 다시 상속 시키고등등 매우 복잡하다. 
※ 그래서 RDB에 저장할 객체에는 절대 상속 관계 객체를 쓰지 않는다. (즉, DAO는 절대 상속 관계 객체여서는 안된다)
DAO(Data Access Object)는 데이터베이스에 접근하는 책임만 담당하는 객체

JPA
-> 애플리케이션 코드와 RDB 사이에서 객체-테이블 매핑을 해준다. 
이 과정에서 JPA는 위에서 살펴보았던 SQL 중심 개발의 문제점을 모두 해결해 준다. 
내 개인적으로 JPA의 가장 큰 장점은 애플리케이션 코드는 그대로 객체 지향적 설계가 가능하게 하고 RDB 설계는 RDB 설계대로 가능하게 하여서
현대 프로그래밍의 패러다임을 전혀 꺠뜨리지 않게 한다는 점인 것 같아. 



JPA를 사용하는 이유(강의 자료 참조)
1. SQL 중심 개발 문제점의 해결
2. 패러다임 불일치 문제 해결
3. 성능
-> JPA紹介 강의 19분 쯤에 언급을 했는데, 즉시/지연 로딩이 있는데, 일반적인 경우, 처음에는 그냥 즉시 로딩으로 설계를 하고, 나중에 지연 로딩으로 할지 즉시 로딩으로 유지할지를 정한다고 한다. 
왜냐하면 설계 단계에서는 연관 관계 객체를 반드시 자주 사용할 지 안 할지 모르기 때문에, 나중에 만약 그 연관 관계 객체가 자주 안 쓰이고 하면 지연 로딩으로 바꾼다고 한다.

4. 생산성
5. 데이터 베이스 벤더 회사로 부터의 독립
-> 이미 대부분의 데이터 베이스 벤더 회사가 JPA의 구현체를 만들어 놓았기 때문에 JPA 인터페이스에 갈아 끼우기만 하면 되고, 클라이언트 코드 변경이 없다.
